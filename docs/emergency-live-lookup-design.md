# 비상연락망 실시간 조회 — 설계안

작성일: 2026-11-17
대상: 구보공영(주) 안전관리 앱 · 비상연락망 게시판 (3. 외부 유관기관 / 4. 지정병원)

---

## 0. 요약 (Executive Summary)

| 항목 | 내용 |
|---|---|
| 현재 상태 | 주소 파싱 기반 **관할 명칭 자동 채움 + 담당자 확인 체크** (구현 완료, 커밋 `d7446ea`) |
| 목표 | 3·4번 항목의 **전화번호·주소·거리를 실제 데이터로 자동 채움** |
| 핵심 결론 | **소방서/경찰서는 API 불필요(정적 데이터 임베드), 지정병원만 실시간 API 필요** |
| 필요 인프라 | Cloudflare Worker 프록시 1개 (무료 한도 내) + 공공데이터포털 API 키 1개 |
| 예상 공수 | 1단계 4~6시간 / 2단계 6~8시간 / 3단계 8~12시간 |
| 예상 비용 | **0원** (Cloudflare Workers 무료 100,000 req/일, 공공데이터포털 무료) |
| 최대 리스크 | API 키 노출 · 응급번호 오표기 → **프록시 + 확인 체크 이중 방어**로 통제 |

**설계의 핵심 판단:** 응급실 전화번호는 바뀌므로 실시간 조회가 가치 있지만, 소방서·경찰서·구청 같은 행정기관은 **연 1~2회만 바뀝니다.** 따라서 후자는 API를 매번 호출할 이유가 없고, 정적 JSON으로 앱에 포함시키는 편이 더 빠르고·무료이며·오프라인에서도 동작합니다. 이 구분이 전체 비용과 안정성을 좌우합니다.

## 1. 현재 구조와 제약

### 1.1 현재 아키텍처

```
┌─────────────────────────────────────┐
│  브라우저 (React 19 + Vite)          │
│  ├─ LocalStorage : 메타데이터         │
│  └─ IndexedDB    : 파일 blob         │
└─────────────────────────────────────┘
         ※ 서버 없음 (백엔드 0)
```

- 배포: 정적 호스팅 (Cloudflare Pages / 사내 웹서버)
- 인증: `gubo_admin_auth` LocalStorage 플래그 (단일 계정 `goobo90`)
- 네트워크 의존: 없음 (완전 오프라인 동작)

### 1.2 왜 직접 API를 못 부르는가

| 제약 | 설명 |
|---|---|
| **API 키 노출** | 프론트엔드 번들에 키를 넣으면 개발자도구로 누구나 추출 가능. 공공데이터포털 키는 일일 트래픽 제한이 있어 도용 시 앱 전체가 차단됨 |
| **CORS** | `apis.data.go.kr` 는 브라우저 직접 호출(CORS)을 허용하지 않음 |
| **응답 형식** | 응급의료기관 API는 **XML만** 제공 → 프록시에서 JSON 변환 필요 |
| **트래픽 제한** | 개발계정은 일 1,000건 수준. 캐싱 없이 매번 호출하면 금방 소진 |

→ **키를 보관하고 XML을 JSON으로 바꿔줄 얇은 서버(프록시)가 반드시 필요합니다.**

## 2. 아키텍처 설계

### 2.1 3계층 구조 (권장안)

```
┌──────────────────────────────────────────────────────────────┐
│ 계층 1 · 정적 임베드 (서버·키·비용 모두 0)                     │
│   소방서 / 경찰서 / 지자체 / 상수도사업소                       │
│   → 빌드 시 포함된 JSON 테이블 (public/data/regions/*.json)    │
│   → 갱신: 연 1회 (수동 또는 CI)                                │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ 계층 2 · 실시간 프록시 (Cloudflare Worker)                     │
│   지정병원 · 응급실 직통번호 · 거리                            │
│   → 주소(시도/시군구)로 조회 → 정규화 JSON 반환                │
│   → 응답 캐시 24시간 (KV) + 브라우저 캐시                      │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ 계층 3 · 오프라인 폴백 (지금 구현된 것)                        │
│   네트워크/API 실패 → 규칙 기반 관할명 + 검색 링크             │
│   → Worker가 죽어도 게시판은 100% 작성 가능                    │
└──────────────────────────────────────────────────────────────┘
```

**설계 원칙: 실시간 조회는 "있으면 좋은 것(enhancement)"이지 "필수 경로"가 아닙니다.** 네트워크가 끊겨도 안전관리자가 게시판을 완성할 수 있어야 하므로, 3계층은 옵션이 아니라 필수입니다.

### 2.2 검토한 대안

| 안 | 방식 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **A** | 현재 방식 유지 (규칙 + 수동 입력) | 서버 0, 완전 오프라인 | 병원 실명·전화번호 자동화 불가 | 보조로 유지 |
| **B** | **하이브리드** (정적 JSON + Worker 프록시) | 비용 0, 오프라인 안전, 유지보수 최소 | Worker 1개 배포 필요 | ✅ **채택** |
| **C** | 전체 실시간 API (매 요청 호출) | 항상 최신 | 트래픽 소진, 오프라인 불가, 응답 지연 | ❌ |
| **D** | 자체 백엔드 (Node/Spring) | 유연성 최대 | 서버·DB·운영 부담, 현재 앱 철학과 배치 | ❌ |

### 2.3 최종 구성도

```
[브라우저]
   │  ① 주소 입력
```

## 4. Cloudflare Worker 프록시 설계

### 4.1 엔드포인트

| Method | Path | 설명 |
|---|---|---|
| `GET` | `/api/emergency/hospitals` | 시도·시군구로 응급의료기관 목록 조회 |
| `GET` | `/api/emergency/health` | 헬스체크 (모니터링용) |

### 4.2 요청 / 응답 명세

**요청**
```
GET /api/emergency/hospitals?q=경기도 용인시 처인구&limit=10
```
| 파라미터 | 필수 | 규칙 |
|---|---|---|
| `q` | Y | 현장 주소 또는 "시도 시군구" 문자열. 최대 60자. 한글·공백·숫자만 허용 |
| `limit` | N | 1~20, 기본 5 |

**응답 (200)**
```json
{
  "ok": true,
  "region": { "sido": "경기도", "sigungu": "용인시" },
  "cached": true,
  "fetchedAt": "2026-11-17T08:30:00Z",
  "hospitals": [
    {
      "name": "용인세브란스병원",
      "category": "지역응급의료센터",
      "erPhone": "031-000-0000",
      "mainPhone": "031-000-0000",
      "address": "경기도 용인시 기흥구 동백중앙로 16",
      "lat": 37.2,
      "lng": 127.1,
      "distanceKm": 3.2,
      "erBeds": 4,
      "accepting": { "뇌경색": true, "복부손상": true, "응급내시경": false }
    }
  ]
}
```

**오류 응답**
| 코드 | 의미 | 클라이언트 동작 |
|---|---|---|
| 400 | `q` 형식 오류 | 입력 안내 메시지 |
| 404 | 해당 지역 응급기관 없음 | 수동 입력 유도 |
| 429 | 레이트 리밋 | 지수 백오프 후 1회 재시도 |
| 502 | 공공 API 장애 | **오프라인 폴백으로 자동 전환** |

### 4.3 Worker 코드 스케치

```ts
// worker/index.ts — Cloudflare Worker
export interface Env {
  DATA_GO_KR_KEY: string;   // Secret (절대 응답에 노출 금지)
  EMERGENCY_KV: KVNamespace; // 24h 캐시
}

const ALLOWED = /^[가-힣0-9\s]{2,60}$/;   // 한글·숫자·공백만
const TTL = 60 * 60 * 24;                  // 24시간
const CORS = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Methods': 'GET,OPTIONS',
};

export default {
  async fetch(req: Request, env: Env): Promise<Response> {
    const url = new URL(req.url);

    if (req.method === 'OPTIONS') return new Response(null, { headers: CORS });
    if (url.pathname === '/api/emergency/health')
      return json({ ok: true, ts: Date.now() });

    if (url.pathname !== '/api/emergency/hospitals')
      return json({ ok: false, error: 'NOT_FOUND' }, 404);

    const q = (url.searchParams.get('q') || '').trim();
    if (!ALLOWED.test(q)) return json({ ok: false, error: 'INVALID_QUERY' }, 400);

    const limit = Math.min(Math.max(Number(url.searchParams.get('limit')) || 5, 1), 20);

    // 1) 캐시 조회
    const cacheKey = `hosp:${q}:${limit}`;
    const hit = await env.EMERGENCY_KV.get(cacheKey, 'json');
    if (hit) return json({ ...hit, cached: true });

    // 2) 지역 분해 (Worker 내 최소 규칙 — 앱의 parseRegion과 결과 일치 필요)
    const { sido, sigungu } = splitRegion(q);
    if (!sido) return json({ ok: false, error: 'NO_REGION' }, 400);

    // 3) 공공데이터포털 호출 (XML)
    const api = new URL(
      'http://apis.data.go.kr/B552657/ErmctInsttInfoInqireService/getEgytListInfoInqire'
    );
    api.searchParams.set('serviceKey', env.DATA_GO_KR_KEY); // 인코딩 키 주의
    api.searchParams.set('Q0', sido);        // 시도
    if (sigungu) api.searchParams.set('Q1', sigungu); // 시군구
    api.searchParams.set('numOfRows', String(limit * 3));
    api.searchParams.set('pageNo', '1');

    let xml: string;
    try {
      const res = await fetch(api.toString(), { cf: { cacheTtl: TTL } });
      if (!res.ok) return json({ ok: false, error: 'UPSTREAM_ERROR' }, 502);
      xml = await res.text();
    } catch {
      return json({ ok: false, error: 'UPSTREAM_UNREACHABLE' }, 502);
    }

    // 4) XML → 정규화 JSON
    const hospitals = parseEmergencyXml(xml).slice(0, limit);
    if (hospitals.length === 0) return json({ ok: false, error: 'EMPTY' }, 404);

    const payload = {
      ok: true,
      region: { sido, sigungu },
      fetchedAt: new Date().toISOString(),
      hospitals,
    };

    // 5) 캐시 저장 후 반환
    await env.EMERGENCY_KV.put(cacheKey, JSON.stringify(payload), { expirationTtl: TTL });
    return json({ ...payload, cached: false });
  },
};

const json = (body: unknown, status = 200) =>
  new Response(JSON.stringify(body), {
    status,
    headers: { 'Content-Type': 'application/json; charset=utf-8', ...CORS },
  });
```

### 4.4 레이트 리밋

- 1차: Cloudflare **Rate Limiting Rules** (IP당 분당 30회)
- 2차: KV 캐시 키를 `시군구 + limit` 로 고정 → 실사용 패턴상 호출량이 매우 낮음
- 3차: Worker 내 `cf.colo` + `CF-Connecting-IP` 기반 간이 카운터 (선택)

### 4.5 캐시 전략

| 계층 | TTL | 근거 |
|---|---|---|
| 브라우저 (`sessionStorage`) | 30분 | 같은 세션 내 재조회 방지 |
| Worker KV | 24시간 | 응급실 전화번호 변경 빈도가 낮음 |
| 공공 API `cf.cacheTtl` | 24시간 | 업스트림 부하 감소 |

**실시간 병상 수(`erBeds`)는 24시간 캐시하면 의미가 없습니다.** 게시판 용도는 "전화번호·주소"이므로 병상 정보는 참고 표시로만 쓰고, 캐시 정책은 24시간으로 유지하는 것을 권장합니다. 실시간 병상이 꼭 필요하면 별도 엔드포인트(`?live=1`, TTL 5분)로 분리합니다.

API는 좌표를 주지만 **현장 좌표를 모르면 거리를 계산할 수 없습니다.** 세 가지 선택지:

| 방법 | 비용 | 정확도 | 권장 |
|---|---|---|---|
| A. API가 주는 시군구 내 목록만 표시하고 거리는 **수동 입력** | 0 | — | 1단계 |

→ **1단계는 A**, 거리 항목은 "약 O.Okm (확인 필요)"로 남기고 담당자가 확인.

## 9. 단계별 로드맵

### 1단계 · 정적 관할 테이블 (4~6시간) ← **가장 효과 큰 작업**

- [ ] 소방서·경찰서·구청 데이터를 시군구 키 JSON으로 변환하는 스크립트 작성
- [ ] `public/data/regions.json` 생성 (gzip 40~60KB)
- [ ] `parseRegion` → `regionCode` 기반 테이블 조회로 교체 (기존 규칙은 폴백으로 유지)
- [ ] 정확도 비교 테스트 (규칙 vs 테이블, 실제 주소 20건)
- **효과:** 소방서·경찰서·구청 명칭 정확도 대폭 상승, 서버 불필요, 오프라인 유지
- **리스크:** 낮음

### 2단계 · Worker 프록시 + 지정병원 조회 (6~8시간)

- [ ] 공공데이터포털 활용신청 (자동승인, 즉시)
- [ ] 활용가이드 HWP에서 **오퍼레이션명·파라미터 확정** ← 선행 필수
- [ ] Worker 작성 + `wrangler secret put DATA_GO_KR_KEY`
- [ ] KV 네임스페이스 생성
- [ ] XML 파서 + 정규화 (curl로 실제 응답 확보 후 작성)
- [ ] 프론트: `useHospitalLookup` 훅 + 후보 선택 UI
- [ ] 실패·타임아웃·오프라인 폴백 테스트
- **효과:** 지정병원 실명·응급실 직통번호 자동 채움
- **리스크:** 중 (API 스펙 미확정, 응답 필드 변동)

### 3단계 · 부가 기능 (8~12시간, 선택)

- [ ] 주소 정규화 API 연동 (도로명 표준화 + `admCd`)
- [ ] 현장 좌표 1회 지정 → 거리·소요시간 자동 계산
- [ ] 병·의원 찾기 API로 경상·주간용(산재지정) 병원 후보
- [ ] 조회 이력·감사 로그 (누가 언제 어떤 데이터를 적용했는지)
- **효과:** 거리·소요시간 자동화, 지정병원 후보 확대
- **리스크:** 중

### 우선순위 근거

1단계가 **비용 0·리스크 최소·효과 즉시**이므로 먼저 합니다. 2단계는 실질 이득(전화번호 자동화)이 크지만 외부 API 의존이 생기므로, 1단계로 안전망을 확보한 뒤 진행합니다.

## 14. 결론

**권장 진행 순서**

```
1단계 (4~6h)  정적 관할 테이블
   └→ 즉시 효과, 서버 0, 오프라인 유지, 리스크 최소
        ↓

   └→ 실질 자동화. API 스펙 확정 후 착수
        ↓
3단계 (선택)  주소 정규화 · 거리 계산 · 병의원 확대
```

**1단계만으로도 "소방서·경찰서·구청이 정확히 채워지는" 효과를 얻고, 지정병원은 지금처럼 검색 링크 + 확인 체크로 운영할 수 있습니다.** 2단계는 그 위에 얹는 개선이며, 실패해도 게시판 기능은 100% 유지됩니다.

현재 구현(커밋 `d7446ea`)은 이미 3계층 폴백 구조를 갖추고 있으므로, 위 설계는 **기존 코드를 버리는 작업이 아니라 확장**입니다.
